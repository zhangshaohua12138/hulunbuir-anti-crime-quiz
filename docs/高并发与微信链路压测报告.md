# 高并发与微信链路压测报告

## 测试范围

- 完整答题链路：登录 → 接受规则 → 开始答题 → 交卷
- OAuth 入口：`/api/auth/wechat`
- 分享配置：`/api/share/config`
- 微信转账：不做真实资金压测，只检查代码边界和现有测试
- 读接口：`/api/health`、`/api/bootstrap`

测试地址：`127.0.0.1:8080`，绕过 Nginx，直接压应用和 SQLite。

## 1. 完整答题链路

### 500 并发

```text
500 用户 / 500 并发
耗时：13.05 秒
吞吐：38.3 组/秒
错误：0
p50：11.29 秒
p95：12.65 秒
p99：12.77 秒
```

### 1000 并发

```text
1000 用户 / 1000 并发
客户端在 15 秒、随后 60 秒超时，未完成统计
服务端仍在线，健康检查 200
```

结论：当前应用在 1000 个用户**同时**完整走链路时不满足可用性要求。

### 1000 总量 / 500 并发

```text
1000 用户 / 500 并发
耗时：27.50 秒
吞吐：36.4 组/秒
错误：0
p50：12.72 秒
p95：14.44 秒
p99：14.47 秒
```

结论：1000 人可以完成，但延迟已经超过 12 秒；适合分散进入，不适合瞬时涌入。

## 2. 读接口

### 12,000 次读请求

```text
12,000 请求 / 200 并发
699.3 RPS
0 错误
p50：283ms
p95：299ms
p99：566ms
```

读接口容量明显高于写链路。

## 3. OAuth 入口

```text
500 并发：0 错误，全部 302，p95 2.22 秒
1000 并发：0 错误，全部 302，p95 4.65 秒
```

注意：这里只验证 OAuth 跳转入口，没有完成微信授权回调。真实 OAuth 还受微信侧限流、网络和用户操作影响。

## 4. 分享配置

```text
20 并发：全部 200，0 错误
```

没有做 500/1000 并发，因为该接口会访问微信接口，继续放大可能影响真实公众号调用额度。它不代表分享动作本身的并发能力。

## 5. 微信转账

没有使用真实商户资金做压测，原因：

- 会产生真实扣款
- 需要真实用户确认收款
- 微信支付有独立风控和频率限制

当前只能确认：

- `out_bill_no` 使用订单 ID，具备幂等键
- 订单状态由服务端控制
- 抽奖和订单创建在同一事务内
- 并发抽奖有测试覆盖
- 真实 APIv3 转账、回调验签、异常重试、对账仍需在微信商户沙箱/小额真实环境验证

## 结论

- **12,000 总参与人数**：有较大把握，需要按活动周期分散进入
- **12,000 人同时在线**：当前架构不满足
- **500 并发完整链路**：可以通过，但 p95 约 12.6 秒
- **1000 并发完整链路**：不通过
- **1000 总量、500 并发**：可以通过，p95 约 14.4 秒
- **OAuth 入口**：1000 并发可响应，但不含真实回调
- **分享**：只做了小规模接口验证
- **转账**：未做真实资金压测

## 上线建议

1. 活动开始前按 500 并发做一次完整演练，并准备降级开关。
2. 若目标为 1000 以上并发，迁移到 PostgreSQL + 多实例 + 队列。
3. 登录/开始答题增加排队或限流，避免瞬时峰值。
4. Nginx 限流阈值要与活动峰值匹配。
5. 微信 OAuth、分享、转账必须在真实微信环境做小额回归。
6. 转账每日对账，异常订单人工复核。
